# Sprint 08 — Introduce ARQ as the Unified Background Processing Platform

## ROLE

You are a Principal Backend Engineer, Distributed Systems Architect, FastAPI Expert, Redis Expert, ARQ Expert, and DDD Software Architect.

Your task is to replace the current background processing implementation with a modern, scalable, asynchronous architecture built on ARQ and Redis.

The goal is to establish a single, consistent background processing platform for the entire backend.

---

# CONTEXT

The project has already been refactored into:

- DDD
- Hexagonal Architecture
- Bounded Contexts
- FastAPI
- PostgreSQL
- SQLAlchemy ORM
- LangChain
- LangGraph

AI workflows already exist (or are being migrated) and must remain unchanged.

This sprint is ONLY responsible for execution, scheduling, orchestration, monitoring, and lifecycle management of background jobs.

Do NOT redesign business logic.

Do NOT redesign LangGraph workflows.

---

# OBJECTIVES

Replace every existing background execution mechanism with ARQ.

Every long-running task in the system must execute through ARQ.

No generation should run inside a FastAPI request lifecycle.

---

# BACKGROUND TASKS

Migrate all asynchronous processes including:

- Job Processing
- Company Processing
- Resume Generation
- Cover Letter Generation
- Skill Roadmap Generation
- Career Insights Generation
- Site Generation
- Generate All Sites
- AI Analysis Tasks
- Future AI Workflows

Every generation must become an ARQ job.

---

# ARCHITECTURE

Target architecture:

Client

↓

FastAPI

↓

Application Service

↓

ARQ Queue

↓

Redis

↓

ARQ Worker

↓

LangGraph Workflow

↓

Repository Layer

↓

PostgreSQL

FastAPI must only enqueue jobs.

Workers execute them.

---

# REDIS

Use Redis only for:

- Job Queue
- Retry Queue
- Delayed Jobs
- Job Metadata
- Progress Cache (if appropriate)
- Worker Coordination

Business data must NEVER be stored in Redis.

Persistent state remains in PostgreSQL.

---

# WORKERS

Create dedicated workers where appropriate.

For example:

workers/

    ai_worker.py

    job_worker.py

    company_worker.py

    resume_worker.py

    roadmap_worker.py

    maintenance_worker.py

Workers should remain lightweight.

Business logic belongs to Application Services and LangGraph.

Workers only orchestrate execution.

Permanent Failure

# FAILURE HANDLING

Failures must never crash workers.

Jobs should move into Failed state.

Failures should contain:

Error Type

Error Message

Stack Trace

Workflow Step

Provider

Timestamp

# CANCELLATION

Support cancelling running jobs.

Workers should stop gracefully.

Workflow state should remain consistent.

---

# TIMEOUTS

Each workflow should define execution timeout.

Long-running jobs should terminate gracefully.
